# CodeNTalk v2 — техническое задание MVP

Версия 0.1 · черновик для обсуждения · август 2026
Статус: **не утверждено**, требует решений владельца по разделу 15.

---

## 0. Контекст и границы документа

CodeNTalk сегодня — бесплатный статический сайт на Next.js: контент лежит в репозитории как типизированные данные, прогресс хранится в `localStorage`, аккаунтов и сервера нет. Английский доведён до уровня C1.

v2 — это переход к платформе с регистрацией, подпиской и несколькими направлениями. Документ описывает **MVP**: минимальную версию, которую имеет смысл показать живым пользователям. Всё, что за его границами, помечено как отложенное, но для отложенного заранее предусмотрено место в схеме данных и API — чтобы потом не переделывать фундамент.

**Что документ сознательно НЕ описывает:** дизайн-макеты, тексты уроков, маркетинг, юридические документы.

### Принципы, которые переносятся из v1

Это не украшение, а ограничения на проектирование:

1. **Никаких счётчиков дней, сердечек и штрафов.** Ошибка ведёт к подсказке и повторной попытке, а не к потере прогресса.
2. **Сначала понимание, потом применение.** Правило человеческим языком до практики.
3. **Контент — это данные, а не код.** Новый урок добавляется без программирования.
4. **Свой темп.** Ученик не обязан успевать к сроку.

> ⚠️ **Внутреннее противоречие, которое нужно решить осознанно.** Мы договорились «зацепить ученика в первые 7 дней», но принцип №1 запрещает стандартный инструмент удержания — стрики. Раздел 5.6 предлагает решение без них. Если оно покажется слабым, придётся выбирать: либо смягчить принцип, либо принять более низкое удержание. Тихо протащить стрики под другим названием — худший вариант.

## 1. Продукт: роли, доступ, монетизация

### 1.1 Роли

| Роль | Кто это | Права |
|---|---|---|
| **Гость** | не вошёл | витрина, описания курсов, первый урок бесплатного курса без регистрации |
| **Ученик (free)** | зарегистрирован, без подписки | английский полностью, введение в веб (HTML/CSS) полностью, прогресс, сертификаты по бесплатным курсам |
| **Ученик (premium)** | активная подписка | всё выше + любые платные курсы в пределах лимита слотов |
| **Администратор** | владелец | управление контентом, пользователями, подписками, просмотр аналитики |

Роль «Преподаватель/автор» в MVP не вводится: единственный автор — владелец. Но поле `role` в таблице пользователей делается расширяемым перечислением, чтобы добавить её без миграции данных.

### 1.2 Модель доступа

Два независимых механизма — их важно не смешивать:

**Механизм 1 — уровень доступа курса.**
Каждый курс имеет `access: free | premium`. Бесплатные: английский (все уровни) и введение в веб (HTML/CSS). Остальные требуют активной подписки.

**Механизм 2 — слоты активных курсов.**
Не больше **двух** курсов одновременно, вариант «активен в этом месяце»: если ученик открыл курс хотя бы раз в календарном месяце, курс занимает слот до конца этого месяца.

Правила, которые нужно зафиксировать явно:

- **Бесплатные курсы слот НЕ занимают.** Иначе freemium теряет смысл: человек попробовал английский и уже не может посмотреть платный курс. Лимит применяется только к `premium`-курсам.
- Слот освобождается **первого числа следующего месяца**, а не через 30 дней после активации. Так проще объяснить пользователю и проще считать.
- Завершённый курс слот **освобождает сразу** — иначе правило наказывает прилежных.
- При попытке открыть третий курс показывается экран с объяснением: какие два слота заняты, когда освободятся, и предложение завершить один из них.
- Прогресс по курсу, который «выпал» из слотов, **сохраняется полностью**. Закрывается только доступ к урокам.

### 1.3 Подписка

Один тариф, без градаций: месячная подписка даёт доступ ко всем платным курсам в пределах слотов. Годовая — опционально, со скидкой (решение отложено, см. 15.3).

Отписка не удаляет аккаунт и прогресс. Вернувшийся через полгода ученик продолжает с того места, где остановился, — это прямо заявленное конкурентное преимущество и его нельзя ломать техническими деталями.

## 2. Контент-модель

### 2.1 Иерархия

```
Track (направление)      англ. язык / веб-разработка / профессия
 └── Course (курс)       уровень или ступень; здесь висит access: free|premium
      └── Module (модуль) одна тема; аналог нынешнего «юнита»
           └── Lesson (урок)
                ├── блоки теории
                ├── упражнения (не влияют на оценку)
                └── (опционально) тест модуля
      └── Exam (итоговый экзамен курса) → сертификат
```

Термин «юнит» из v1 переименован в **модуль**: в v2 «юнит» путается с единицей подписки.

### 2.2 Где живёт контент — ключевое архитектурное решение

**Решение для MVP: контент остаётся в репозитории как типизированные данные; в базе хранятся только пользовательские записи.**

Обоснование:
- Главная сила v1 — контент как данные под контролем версий. Правки видны в диффе, откат тривиален.
- Полноценный редактор курсов — это отдельное приложение на сотни экранов. Строить его ради одного автора нельзя.
- Статическая генерация страниц уроков даёт скорость и дешёвый хостинг.

Плата за это решение и как её гасим:
- Чтобы менять текст урока, нужен деплой. Приемлемо: автор один, деплой автоматический.
- Прогресс ссылается на уроки, поэтому **у каждого урока обязателен стабильный неизменяемый `slug`**, а в БД — таблица-зеркало `courses/modules/lessons`, наполняемая сид-скриптом при каждом деплое. Скрипт обязан падать с ошибкой, если урок, на который есть прогресс, исчез из репозитория. Без этой проверки прогресс будет молча биться.
- Миграция на редактируемый в БД контент запланирована как отдельная задача фазы 6, схема к ней готова заранее.

### 2.3 Типы учебных блоков

Переносятся из v1 (проверены на 800+ заданиях): теория, выбор варианта, сборка фразы из слов, вставка пропущенного слова, аудирование, чтение с вопросами, многофразное аудирование.

Добавляются для v2: **код с предпросмотром** (фаза 8), **развёрнутый письменный ответ** с эталоном и чек-листом самопроверки (уже есть в v1).

## 3. Пользовательские сценарии

### 3.1 Первый визит гостя

1. Витрина: направления, честное «что бесплатно, что по подписке».
2. Клик по английскому → каталог уровней → **первый урок открывается без регистрации**. Это принципиально: человек должен увидеть продукт до того, как его попросят о чём-либо.
3. В конце первого урока — предложение сохранить прогресс, то есть зарегистрироваться. Не раньше.

### 3.2 Регистрация и онбординг

1. Почта, пароль, имя. Никаких лишних полей.
2. Подтверждение почты — **не блокирует** вход; напоминание висит баннером. Блокировка на этом шаге убивает конверсию.
3. Три коротких вопроса: что хочешь изучать → зачем (карьера / учёба / для себя / переезд) → сколько времени в неделю готов уделять.
4. Для языка — предложение пройти тест уровня (можно пропустить).
5. Итог: персональная рекомендация «начни отсюда» с одной кнопкой. Не список из 40 курсов.

### 3.3 Основной цикл обучения

1. Кабинет показывает **одну главную кнопку** — «Продолжить: модуль 3, урок 2». Это самый важный элемент интерфейса.
2. Урок: теория → упражнения по ходу → отметка о прохождении.
3. Позиция внутри урока сохраняется автоматически, возврат — на то же место.
4. Конец модуля — тест модуля.
5. Конец курса — экзамен, при сдаче — сертификат PDF.

### 3.4 Ученик берёт платный курс

1. Открывает курс с меткой «по подписке».
2. Нет подписки → экран с ценой и понятным «что входит».
3. Есть подписка, слоты свободны → курс активируется, слот занят до конца месяца.
4. Слоты заняты → экран с объяснением, какие курсы занимают слоты и когда освободятся.

## 4. UX: что берём у Coursera, Udemy и Kajabi

Копируем **поведение**, а не оформление.

| Источник | Паттерн | Как применяем |
|---|---|---|
| Coursera | Явная структура пути и «где я сейчас» | Полоса модулей вверху курса, всегда видно текущий шаг |
| Coursera | Итоговая проверка знаний, а не просто просмотр | Экзамен курса с порогом сдачи |
| Udemy | Свой темп, возврат в любой момент | Автосохранение позиции, кнопка «Продолжить» |
| Udemy | Оценка длительности | «~12 минут» у каждого урока |
| Kajabi | Единый кабинет: курсы, прогресс, сертификаты в одном окне | Кабинет как домашняя страница вошедшего |
| Kajabi | Ощущение личной программы, а не магазина | Никакой витрины с ценниками внутри кабинета |

**Чего не берём осознанно:** видеоплеер как центр урока (видео не будет), рейтинги и отзывы на курсы (один автор — рейтинг бессмысленен), маркетплейс-логику «купи этот курс со скидкой 90%».

### 4.1 Кабинет — состав экрана

Сверху вниз:
1. «Продолжить» — курс, модуль, урок, оценка времени. Одна кнопка.
2. Мои курсы: карточки с полосой прогресса, метка занятого слота и датой освобождения.
3. Ближайшая цель: «до конца модуля 2 урока» или «до сертификата 1 экзамен».
4. Сертификаты.
5. Состояние подписки — компактной строкой, без давления.

### 4.2 Прогресс

- Прогресс урока: не начат / в процессе / пройден.
- Прогресс модуля: доля пройденных уроков + статус теста.
- Прогресс курса: доля модулей + статус экзамена.
- **Проценты не показываем как единственную метрику** — показываем «пройдено 7 из 12 уроков». Числа честнее и не создают ложного ощущения близости к финишу.

### 4.3 Сертификаты

- Выдаётся при сдаче экзамена курса с порогом (по умолчанию 70%).
- PDF: имя, курс, дата, итоговый балл, уникальный серийный номер, ссылка на публичную проверку.
- Публичная страница `/certificate/<serial>` — без авторизации, показывает подлинность. Это то, что человек отправит работодателю.
- Отзыв сертификата возможен админом (поле `revoked_at`).

## 5. Педагогика

### 5.1 Размер урока

Без drip-контента дозировку задаёт **сам размер урока**. Норматив: **8–15 минут**, один смысловой шаг, максимум одна новая грамматическая или техническая идея. Урок, который не читается за 15 минут, подлежит разбиению — это правило для автора, а не пожелание.

### 5.2 Рекомендованный порядок

Уроки идут по порядку, следующий подсвечен как рекомендованный. Перепрыгнуть можно — блокировок нет. Исключение: экзамен курса открывается только после прохождения всех модулей, иначе сертификат обесценивается.

### 5.3 Упражнения против тестов

Разделение принципиальное, и его нужно донести до ученика интерфейсом:

|  | Упражнения | Тесты |
|---|---|---|
| Цель | научить | проверить |
| Ошибка | подсказка и повтор | учитывается в балле |
| Попытки | не ограничены | ограничены |
| Подсказки | есть | нет |
| Влияние на сертификат | нет | да |

### 5.4 Тесты — требование «настоящие и серьёзные»

Чтобы тест действительно проверял знания, а не память на порядок кнопок:

- **Банк вопросов.** В тесте модуля показывается 10 вопросов из банка на 25–30. Повторная попытка даёт другую выборку.
- **Перемешивание** вопросов и вариантов ответа при каждой выдаче.
- **Позиция правильного ответа контролируется.** В v1 уже был случай: во всех 20 вопросах теста уровня правильный ответ стоял первым, и тест проходился нажатием первой кнопки. Для банка вопросов вводится автоматическая проверка распределения позиций в CI.
- **Разные типы вопросов**, не только выбор из четырёх: вставка слова, сопоставление, установка порядка, короткий ответ с проверкой по нормализованной строке.
- **Метка темы** у каждого вопроса. По результату ученик видит не «6 из 10», а «слабое место — прошедшее время», со ссылкой на конкретный урок.
- Экзамен курса: 25–30 вопросов, ограничение по времени, порог 70%, не больше 3 попыток в сутки.

### 5.5 Домашние задания и проверка

В MVP — **самопроверка**: развёрнутый ответ, затем эталон и чек-лист. Ручной проверки нет (один автор не вычитает тысячи работ), автоматической проверки эссе нет (отложено до AI-наставника, фаза 9).

### 5.6 Удержание в первые 7 дней — без стриков

Инструменты, не нарушающие принцип «без счётчиков и штрафов»:

1. **Быстрая первая победа.** Первый урок короче обычного и заканчивается ощутимым результатом.
2. **Всегда одна следующая кнопка.** Ученик никогда не видит экран без очевидного следующего шага.
3. **Первая веха на 3-й день, а не на 30-й.** Небольшой модуль завершается отметкой о достижении. Это не бейдж за серию дней — это отметка за реальный объём работы.
4. **Письма по содержанию, а не по расписанию.** «Ты остановился на модуле 2, следующий урок — про время в прошлом, 9 минут» вместо «Ты не заходил 3 дня!». Три письма: день 1, день 3, день 7.
5. **Возврат без чувства вины.** Вернувшемуся показывается «продолжим с того места», а не «ты пропустил 14 дней».

**Метрика успеха фазы 5:** доля зарегистрированных, прошедших хотя бы 3 урока за первую неделю. Целевой ориентир задаётся после первых 100 регистраций, гадать заранее бессмысленно.

### 5.7 Q&A и достижения

Отложены. Для Q&A заранее фиксируется решение: это **структурированные вопросы с привязкой к уроку**, а не лента комментариев. Лента комментариев в обучающем продукте вырождается в спам, и модерировать её в одиночку невозможно.

## 6. Техническая архитектура

### 6.1 Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Фронтенд | Next.js 15, App Router, TypeScript | уже используется, статика для контента, серверные компоненты для кабинета |
| Стили | CSS-модули + токены | перенос из v1, без переписывания на Tailwind |
| Бэкенд | Route Handlers Next.js (`/api/*`) | отдельный сервер для MVP избыточен; при росте выносится без переписывания контрактов |
| БД | PostgreSQL | транзакции для подписок, JSONB для гибких полей заданий |
| ORM | Prisma | миграции, типы из схемы |
| Авторизация | Auth.js (NextAuth) | почта+пароль сейчас, OAuth позже без переделки |
| Файлы | Cloudflare R2 или S3 | PDF-сертификаты, будущие материалы |
| Почта | Resend или Postmark | подтверждение почты, письма удержания |
| Хостинг | Vercel + управляемый Postgres (Neon/Supabase) | уже есть аккаунт и налаженный деплой |

### 6.2 Готовность к мобильному приложению

Мобилка отложена, но решения принимаются сейчас:

1. **Вся бизнес-логика — за HTTP API.** Ни одно правило (лимит слотов, подсчёт балла, выдача сертификата) не живёт только в React-компоненте.
2. **Единый контракт.** Веб-клиент ходит в те же `/api/*`, что потом будет использовать приложение. Никаких «серверных срезаний углов» ради веба.
3. **Авторизация по токену**, пригодному для мобильного клиента, а не только по httpOnly-куке. Auth.js настраивается на выдачу и того, и другого.
4. **Контент отдаётся структурой, а не готовым HTML.** Тогда приложение отрисует его нативно.
5. Версионирование API с первого дня: префикс `/api/v1/`.

### 6.3 Слои

```
app/                      страницы и серверные компоненты
  (marketing)/            витрина для гостей
  (app)/                  кабинет, курсы, уроки — требует входа
  api/v1/                 HTTP API — единственный вход в бизнес-логику
lib/
  domain/                 чистые правила: слоты, баллы, сертификаты (без БД и React)
  db/                     Prisma-клиент и запросы
  auth/
  billing/                провайдер платежей за интерфейсом
  ai/                     наставник за интерфейсом
content/                  курсы как типизированные данные
scripts/
  seed-content.ts         зеркалирование контента в БД + проверка целостности
```

Ключевое: `lib/domain/` не знает ни про базу, ни про React. Правила покрываются модульными тестами и переиспользуются мобильным приложением через API.

## 7. Схема базы данных

Ниже — рабочий черновик. Типы указаны для PostgreSQL.

### 7.1 Пользователи и доступ

```sql
users
  id                uuid pk
  email             citext unique not null
  password_hash     text                       -- null, если вход через OAuth
  display_name      text not null
  role              text not null default 'learner'   -- learner | admin
  email_verified_at timestamptz
  onboarding        jsonb                      -- цель, время в неделю, интересы
  created_at        timestamptz not null
  last_seen_at      timestamptz

subscriptions
  id                    uuid pk
  user_id               uuid fk -> users
```

## 9. Авторизация и безопасность

- Пароли — Argon2id (не bcrypt).
- Ограничение частоты: вход, регистрация, восстановление пароля, отправка теста, обращения к ИИ.
- Сессии — httpOnly-кука для веба и Bearer-токен для будущего приложения.
- **Проверка прав только на сервере.** Скрытая в интерфейсе кнопка — не защита: каждый эндпоинт заново проверяет подписку и слот.
- Тесты: правильные ответы **никогда не уходят на клиент** до отправки попытки. В v1 это было неважно (нет оценок), в v2 — критично для ценности сертификата.
- Персональные данные: минимум — почта и имя. Экспорт и удаление аккаунта по запросу.
- Все денежные операции — только по вебхукам провайдера, не по редиректу «успешно» с фронта.

## 10. Платежи

### 10.1 Серьёзная проблема, требующая решения до разработки

**Stripe не поддерживает Казахстан для приёма выплат.** Если юрлицо или ИП зарегистрированы в РК, план «просто подключим Stripe» не сработает. Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Paddle / Lemon Squeezy** (merchant of record) | берут на себя налоги и НДС по странам, работают с РК | комиссия выше (~5%), меньше контроля |
| **Локальные (Freedom Pay, CloudPayments KZ, Kaspi)** | тенге, привычные ученику способы оплаты, ниже комиссия | сложнее с зарубежными картами, документация слабее |
| **Юрлицо за рубежом** | Stripe целиком | расходы и бухгалтерия за границей |

Решение зависит от того, где регистрируется бизнес и кто основная аудитория — это вопрос к владельцу (15.1).

### 10.2 Как проектируем, чтобы не зависеть от выбора

Провайдер прячется за интерфейсом:

```ts
interface BillingProvider {
  createCheckout(userId, plan): Promise<{ redirectUrl: string }>;
  createPortalLink(userId): Promise<{ redirectUrl: string }>;
  parseWebhook(req): Promise<BillingEvent>;
}
```

В MVP работает `StubBillingProvider`: переключает подписку в базе без денег, что позволяет полностью разработать и протестировать логику доступа. Подключение настоящего провайдера — замена одной реализации.

### 10.3 Обязательные сценарии

Неудачное списание, отмена, возврат, смена карты, повторная подписка после перерыва, ручная выдача доступа админом. Отмена — **в один шаг** из кабинета, без «напишите в поддержку»: это и требование законов ряда стран, и вопрос доверия.

## 11. AI-наставник

Отложен до фазы 9, но контракт фиксируется сейчас.

- **Схема:** RAG по материалам конкретного курса, а не свободная беседа. Наставник обязан отвечать в рамках курса и признавать незнание.
- **Роль:** подталкивать, а не решать за ученика. В упражнении — подсказка, не ответ.
- **Контекст:** прогресс ученика и его типичные ошибки.
- **Стоимость.** Это главный риск. Обязательны: лимит обращений в сутки, кэш повторяющихся вопросов, дешёвая модель по умолчанию и дорогая только для сложных случаев, отдельный бюджет с оповещением.
- **Безопасность:** фильтрация ввода, защита от попыток вытащить ответы теста через наставника.

## 12. Выполнение кода

Отложено до фазы 8. Важное наблюдение, влияющее на планирование:

- **HTML, CSS и JavaScript выполняются прямо в браузере** в изолированном `iframe` с `sandbox`. Сервер не нужен, стоимость нулевая. Схема «код слева, результат справа» для бесплатного курса по вебу делается без инфраструктуры.
- **Python, C#, C++ требуют серверной песочницы** (Judge0 или собственные контейнеры с ограничением памяти, времени и сети). Это дорого и рискованно.

Отсюда вывод для дорожной карты: практику в вебе можно запустить рано и дёшево, а серверные языки — только после того, как подписка начнёт приносить деньги.

## 14. Фазы работ

Оценка в неделях не даётся: сроков нет, важен порядок. Каждая фаза заканчивается работающим состоянием.

| Фаза | Содержание | Готово, когда |
|---|---|---|
| **0. Фундамент** | репозиторий, Prisma, миграции, Auth.js, деплой, CI | можно зарегистрироваться и войти |
| **1. Контент и чтение** | сид-скрипт, каталог, страница урока, прогресс, «продолжить» | английский проходится целиком с сохранением прогресса |
| **2. Практика и тесты** | упражнения, банк вопросов, тесты модулей, экзамен, разбор слабых тем | тест реально проверяет знания |
| **3. Сертификаты и кабинет** | PDF, публичная проверка, кабинет | сертификат можно отправить работодателю |
| **4. Доступ** | подписка-заглушка, слоты, гейты freemium | платный курс недоступен без подписки, лимит работает |
| **5. Онбординг и удержание** | анкета, рекомендация, письма, первая веха | новичок за 7 дней доходит до 3 уроков |
| **6. Админка** | управление пользователями, сводка, редактор контента | контент правится без деплоя |
| **7. Платежи** | выбранный провайдер, вебхуки, портал управления | принимаются реальные деньги |
| **8. Код в браузере** | предпросмотр HTML/CSS/JS | курс по вебу с практикой |
| **9. AI-наставник** | RAG по курсу, лимиты, стоимость | наставник отвечает по материалам |
| **10. Мобильное приложение** | клиент поверх готового API | приложение в сторах |

Фазы 0–5 составляют MVP. Фазы 6–10 — развитие.

### Что делать с текущим сайтом

Рекомендация: **v2 разрабатывается как отдельный проект**, v1 продолжает работать. Контент английского переносится сид-скриптом — он уже в правильном формате. Переключение доменa — после того, как v2 догонит v1 по объёму английского. Ломать работающий сайт ради переезда незачем.

## 15. Открытые вопросы — решения за владельцем

Без ответов на первые три разработку фазы 7 начинать нельзя.

1. **Юрисдикция бизнеса.** Где регистрируется ИП или ТОО? От этого зависит выбор платёжного провайдера (раздел 10.1).
2. **Основная аудитория по географии.** Казахстан или шире? Влияет на валюту, способы оплаты и язык интерфейса.
3. **Цена подписки и валюта.** Тенге, доллары? Есть ли годовой тариф со скидкой?
4. **Пробный период.** Бесплатные 7 дней или роль пробника выполняет бесплатный английский? Моя рекомендация — **второе**: бесплатный курс уже есть, а пробный период добавляет мошенничество и сложность.
5. **Языки интерфейса.** Русский обязательно. Казахский? Английский?
6. **Возвраты.** Условия и срок.
7. **Что показывать по завершённым курсам после отписки** — доступ к материалам закрыт, но сертификат остаётся навсегда. Подтвердить.
8. **Порог сдачи экзамена** — 70% по умолчанию, менять ли по курсам.

## 16. Организация работы

### 16.1 Роли агентов

Владелец — CTO и заказчик, принимает решения. Дальше:

| Роль | Зона ответственности | Что отдаёт дальше |
|---|---|---|
| **PM** | единственная точка общения с владельцем, порядок работ, приёмка | задачу следующему |
| **Архитектор** | схема БД, контракты API, границы модулей | спецификацию разработчикам |
| **Бэкенд** | API, домен, миграции, интеграции | работающие эндпоинты |
| **Фронтенд** | экраны, состояния, доступность | интерфейс поверх API |
| **QA** | тесты, проверка граничных случаев | отчёт о дефектах |

Правило: **никто не начинает работу без письменного контракта от архитектора.** Иначе фронтенд и бэкенд разойдутся в понимании API, и это вскроется поздно.

### 16.2 Порядок работы над контентом

По одной теме за раз, как договорились: разбираем учебник → составляем программу модуля → пишем уроки → пишем банк вопросов → проверяем целостность автоматикой → показываем владельцу.

### 16.3 Обязательные автоматические проверки

Уроки в v1 показали, где ломается:

- у каждой группы вариантов ровно один правильный ответ;
- в заданиях на сборку фразы порядок слов действительно даёт ответ;
- позиция правильного ответа в банке вопросов распределена равномерно;
- ни один урок с существующим прогрессом не исчез из репозитория;
- все ссылки на правила ведут в существующие якоря.
